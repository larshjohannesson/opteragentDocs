# Incident: OrderCheck search — slow responses, UI freezes, and OutOfMemoryExceptions

**Status:** Under investigation — root cause not fully confirmed, contributing factors identified
**Scope:** Fleet-wide (133 customers, 636 OrderCheck OOM crashes in the last 90 days; 91 customers, 260 crashes in the last 30 days); UI freeze pattern confirmed in detail for one customer
**Date of write-up:** 2026-09-03
**Related:** [PR #13088 "Move OrderCheck search off the UI thread"](https://opter.ghe.com/code/Main/pull/13088) (open since 2026-06-17, unreviewed)

## Summary

Customers searching in Order Control (OrderCheck) intermittently experience either a frozen application (up to 21+ minutes observed) or a hard failure dialog ("Fel vid hämtande av data — Kontakt din systemadministratör"). Both symptoms trace back to the same server-side code path: `OrderCheck.GetAllSimpleResult` → `OrderCheck.LoadSearchResultModelsFromDataSet`. The failure dialog case has been confirmed to be a genuine `System.OutOfMemoryException` server-side, occurring for **133 different customers, 636 times, in the last 90 days** (91 customers, 260 times, in the last 30 days) — this figure includes crashes that fail earlier in the pipeline, during `ExecuteDataSet`'s post-processing step, before execution ever reaches OrderCheck's own C# code (see Fact #3 below; an earlier pass undercounted this by about half). The freeze case has been confirmed via DeadlockWatchdog telemetry to be a real multi-minute block on the UI thread, not a false positive.

For context, OrderCheck accounts for the large majority (~86%) of all `OutOfMemoryException`s in `Opter.Main.ServerApi`: the remaining ~14% (105 occurrences, 24 customers, 90 days) come from unrelated features — the Statistics API, single-order loading, Dispatch, and auto-dispatch route planning — that share the same underlying architectural pattern (see "Other ServerApi OOM sources" below) but are not part of this incident's scope.

Investigation found a long-standing structural weakness in how OrderCheck materializes search results, a client-side design flaw that turns any slow server response into a full application freeze, and a correlation with the .NET 9 → .NET 10 runtime upgrade that shipped between the `2025.06` and `2025.12` release branches. No single root cause has been conclusively isolated; several contributing factors have been identified and are ranked below.

**Update**: the OOM crashes and the UI freezes were initially treated as likely sharing one mechanism (memory pressure). Direct pod telemetry during two independent, known long-freeze windows argued against an *active* version of that — the pod does no extra visible work (flat memory, near-zero CPU) during either freeze, not struggling in real time. See "Freeze mechanism" below. But a later, much larger fleet-wide check (20,041 crash-free freeze episodes) found that the pod's memory *going into* a freeze — measured strictly beforehand, not during — sits at roughly double the fleet-wide typical baseline. So memory pressure isn't absent from the freeze story after all; it just shows up as a predisposing starting condition rather than active real-time strain. The OOM crashes remain a confirmed, undisputed server-side memory/allocation failure; the freezes look like a related but distinct mechanism (most plausibly a slow/blocked SQL query that takes longer specifically when the pod is already running memory-hot) sharing the same vulnerable, synchronous-on-the-UI-thread code path.

**Working synthesis**: this incident is best understood as **two overlapping problems sharing the same vulnerable OrderCheck search code path, not one problem with two symptoms**:
1. **An increased tendency toward OOM crashes on broad OrderCheck searches.** The mechanism is a long-standing, undisputed inefficiency in how OrderCheck materializes search results server-side (the `Clone<T>()` fan-out and unbounded `DataSet` materialization — see "Strong inferences" below), which has always been capable of exhausting memory on a large enough result set. It is surfacing *more often* now not because the code got worse (confirmed — no substantive diff between `2025.06` and `2025.12`, Fact #11) but because `2025.12`'s runtime carries a confirmed higher idle memory baseline (Fact #15), leaving less headroom in the pod before the same size of query pushes it over the limit. Directly corroborated by customer/support testimony on the same ticket that produced the confirmed crash — see Fact #16.
2. **A separate, likely-database-side mechanism causing intermittent multi-minute freezes, with pod memory level as a probable contributing/predisposing factor rather than an independent cause.** Pod telemetry during two known freezes shows no *active* memory/CPU strain during the freeze itself, but a fleet-wide check across 20,041 crash-free freezes shows the pod's memory running roughly 2x the typical baseline in the minutes *before* each one starts (see "Freeze mechanism" below, Fact #20). The underlying slow-response mechanism is still most plausibly SQL-side and not yet confirmed — pending an execution plan or blocking-chain capture (Recommended next steps, #2) — but it may be that a slow query takes longer specifically when the pod has less memory headroom to work with, rather than pod memory and SQL slowness being fully unrelated.
3. **The two problems are coupled through shared human/business triggers and a post-crash memory carryover effect, even though their immediate mechanisms differ.** A detailed case study (Apollo Budbiler, see "Behavioral and load coupling" below) shows multiple employees independently attempting the same broad search (a shared business task, not coincidence) within a tight window, and — critically — the pod that threw an OOM exception did not release the memory afterward, staying elevated for 30+ minutes and leaving less headroom for the next request that happened to land on it. This gives a concrete mechanism (not just correlation) for why freezes and crashes cluster together in time for the same customer, on top of the underlying "one crash, many colleagues retrying" behavioral dynamic — and it's the same lever as point 2 above: elevated pod memory correlates with both worse post-crash freeze activity and crash-free freeze onset.

## Facts (directly observed/confirmed)

1. Multiple customers have reported slow OrderCheck searches and hard error dialogs.
2. At least one confirmed case (itide.no, [ticket #149308](https://opter.freshdesk.com/a/tickets/149308), 2026-08-31) traced the error dialog directly to a server-side `System.OutOfMemoryException` thrown in `Opter.Main.Server.Orders.OrderCheck.OrderCheck.LoadSearchResultModelsFromDataSet`, called from `GetAllSimpleResult`. The same ticket also carries independent customer/support testimony naming `2025.12` as the version where this broke — see Fact #16.
3. The identical underlying bug has occurred for **91 distinct customers, 260 times, in the last 30 days** (133 customers, 636 times, in the last 90 days) — this is a fleet-wide issue, not isolated to one customer. This figure combines two manifestations of the same root cause: crashes where the stack trace explicitly names `OrderCheck`/`LoadSearchResultModelsFromDataSet` (the manifestation an earlier pass of this investigation counted alone — 260/91 90-day, i.e. undercounting by about half), and crashes that fail one step earlier in the pipeline, inside `DatabaseAccess.ExecuteDataSet`'s post-processing (`AdjustTimeZoneToLocalTime`), before execution ever reaches OrderCheck's own C# code — identifiable only via the `Message` field, which logs the actual stored procedure called (`k2_orc_get_all`/`k2_orc_get_all_by_all`). See "Other ServerApi OOM sources" below for how this was found and what else shares the same underlying pattern.

5. The client makes this call **synchronously on the UI thread**: `SearchCommand` is a plain (non-async) `RelayCommand` whose handler calls `CallerBase.RestCall`, which blocks via `.GetAwaiter().GetResult()`. Confirmed by direct code inspection ([OrderCheckViewModel.cs](../../Main/Order/ViewModels/Order/OrderCheck/WPF/OrderCheckViewModel.cs), [CallerBase.cs](../../Main/ServerProxy/CallerBase.cs)), not inferred.

The rate gap is present from the first week of the 90-day window, before the `2025.06`→`2025.12` migration wave accelerated — it is not an artifact of the migration itself, though it is noisier week-to-week than a clean, monotonic law.

## Strong inferences (well-supported, not directly measured)

- **The server was genuinely slow to respond during freezes, not the client hanging on its own.** The UI thread was observed blocked *inside* the outbound REST call for up to 21 minutes (via DeadlockWatchdog stack traces showing the wait inside `CallerBase.RestCall`/`Task.InternalWait`). Nothing else explains a call staying outstanding that long.
- **`LoadSearchResultModelsFromDataSet`'s reflection-based `Clone<T>()` fan-out is the mechanical cause of the OOM crashes.** Its role in the *freezes* specifically is now weaker than earlier reasoning suggested — see "Freeze mechanism" below; it may still contribute to ordinary slowness on moderately-large searches (the CPU cost of reflection over ~350 properties per cloned row is real regardless of freeze duration), but it is no longer the leading explanation for multi-minute freezes specifically. Mechanism, from code inspection ([OrderCheck.cs:221-306](../../Main/Server/Orders/OrderCheck/OrderCheck.cs)):
  - `GetAllSimpleResult` loads the **entire** multi-table result into an in-memory `DataSet` via `_databaseAccess.ExecuteDataSet(...)` — no streaming (`SqlDataReader`), no row cap, no `TOP`/pagination anywhere in the SQL layer either (`k2_orc_get_all` → `k2_orc_get_all_by_all` → the 2816-line `k2_search_deliveries_common_output`, ~200+ output columns).
  - `LoadSearchResultModelsFromDataSet` materializes one `OrderCheckSearchResult` object per row — a wide DTO with ~350 properties.
  - For Consignment/Shipment/PriceItemCost search modes, every shipment/price-item beyond the first calls `ModelBase.Clone<T>()` ([ModelBase.cs:76-100](../../Main/Model/ModelBase.cs)), which reflects over **all ~350 properties** to produce a full duplicate object — not a lean child row. A delivery with 10 shipments costs 11 full-size objects instead of 1 large + 10 small. This is an O(rows × fanout) memory (and CPU) multiplier with no ceiling.
  - No safeguard exists anywhere: no max-row check, no warning, no TODO acknowledging the risk.

## Freeze mechanism: pod telemetry during known freeze windows

Earlier reasoning treated pod memory pressure as a plausible cause of both the OOM crashes and the intermittent freezes — the logic being that a pod running chronically close to its memory ceiling would need more frequent/expensive GC passes, which could stall request processing without necessarily crashing. Checking this directly, against fine-grained (5-minute-interval) pod telemetry during two independent, precisely-known freeze windows, does not support it.

**21.75-minute freeze, Markis City Service, 2026-09-01, 07:23:55–~07:45** (pod `markiscityse-serverapi-79f9ff95cf-jt2d8`):

But it isn't independent of memory either — see "Ambient memory baseline and crash-free freezes" immediately below, which found that pods are typically already running hot *before* a freeze starts, fleet-wide. The most coherent picture: the freeze itself is most plausibly a slow/blocked SQL query (execution time, or lock/blocking contention on the DB side — see the "slow SQL response" hypothesis below), and an already-elevated pod memory baseline is a probable contributing factor to *why* that query is slow this time (less GC headroom, more expensive allocations along the way) rather than a fully separate, unrelated mechanism. The OOM crash mechanism (`Clone<T>()` fan-out exhausting the pod's memory on a large-enough result) is unchanged and remains the confirmed, distinct cause of the crashes specifically.

This was checked on 2 of 263 freeze episodes for one customer — illustrative, not by itself proof it holds fleet-wide (the fleet-wide check below covers that). Both checked episodes were *isolated* freezes with no crash on the same pod nearby in time. See "Behavioral and load coupling" below for a case (Apollo Budbiler) where a freeze cluster *did* coincide with an actual crash — there, the picture is different: the crash-throwing pod's memory does climb and stay elevated, just not during the freeze that preceded the crash itself.

## Ambient memory baseline and crash-free freezes (fleet-wide check)

The two examples above only test whether a pod does *extra* work *during* a freeze. They don't test whether the pod's *starting* memory level (before the freeze even begins) predicts anything — and freezes that have no nearby crash are the cleanest way to test that, since there's no crash-driven memory carryover to confound the picture.

**Method**: find every freeze *start* event (`missCount == 1` in the DeadlockWatchdog payload, tied to `GetAllSimpleResult`) in the last 30 days, exclude any within ±60 minutes of an OOM crash for that same customer, leaving **20,041 crash-free freeze episodes** fleet-wide. For each, look up that customer's pod memory using only samples from 2-30 minutes *before* the freeze started (strictly preceding, so it can't just be the same slow request's own in-flight allocation). Compare that to a fleet-wide **unconditional baseline**: average pod memory % across all 5.3M `ServerApi` samples in the same window, freeze or no freeze.

| | Median memory % of limit | Mean | IQR |
|---|---|---|---|
| Fleet-wide unconditional baseline | 18.9% | 21.3% | 12.2–27.1% |
| Pod memory 2-30 min *before* a crash-free freeze | **34.4%** | 35.6% | 27.2–42.9% |

Roughly double the typical baseline, measured strictly before the freeze began. This generalizes what the two Markis examples showed in passing (53.6-55.6%, well above baseline) into a fleet-wide, 20,041-episode pattern: **freezes preferentially happen on pods that are already running memory-hot, even with no crash anywhere nearby.** Combined with "Behavioral and load coupling" below (crashes that leave a pod heavier correlate with worse subsequent freezes), the picture is now one continuous relationship rather than two disconnected facts: ambient pod memory level predicts freeze propensity in general, and anything that pushes that baseline up — a `2025.12`/.NET 10 pod's higher idle floor (Fact #15), a recent crash that didn't fully release memory (Fact #19), or simply concurrent load from a shared business task — makes a freeze somewhat more likely on top of it.

**Caveat**: this is a correlational, aggregate comparison, not a controlled experiment — it doesn't rule out a shared cause (e.g. sustained high overall traffic independently drives both higher ambient memory and more freezes) rather than memory level itself being causal. It's also worth noting explicitly: this shows *elevated baseline correlates with freeze onset*, not that the pod is doing more active work *during* the freeze — that part of the original "Freeze mechanism" finding (flat CPU/memory in the two checked episodes) still stands.

## Behavioral and load coupling between freezes and crashes (Apollo Budbiler case study)

The "Freeze mechanism" findings above show that an *isolated* freeze, on a pod with no recent crash, doesn't look like a memory-pressure event. That doesn't rule out a *different* kind of coupling: multiple people independently attempting the same broad, risky search around the same time (a shared business trigger, e.g. "pull last year's orders for a report"), and a crash on one pod leaving that pod more fragile for whoever's request lands there next. The Apollo Budbiler incident behind [ticket #149027](https://opter.freshdesk.com/a/tickets/149027) (Fact #17) shows exactly this, with both parts directly observable in the telemetry.

**Timeline, 2026-08-26 (all times UTC)**:

| Time | Event |
|---|---|
| 06:53 | THOMASH: brief freeze (7s), recovers |
| 06:54 | BENDAVID logs in |
| 06:56:33 → 06:59:49 | BENDAVID: one continuous freeze, building for **3 minutes straight** (`missCount` climbing 1→29) |
| **06:59:50.1357** | `apollono-serverapi-54789cf6d5-2j7b8` throws the `OutOfMemoryException` |
| 06:59:56 | BENDAVID's freeze **recovers** — 6 seconds after the server-side crash |
| 07:08–07:16 | GEIRSSURFACE (Geir) and JOAKIMS both log in and hit repeated freezes; JOAKIMS's own client-side heap climbs **98 MB → 416 MB → 596 MB → 645 MB** across consecutive retries in ~8 minutes |

BENDAVID's freeze recovering 6 seconds after the crash strongly suggests BENDAVID's own search *is* what caused it — the "freeze" was the client blocked waiting on the request that eventually failed server-side with an OOM.

**Pod memory, before and after the crash** — Apollo runs **three concurrent `ServerApi` pods** (`2j7b8`, `cxqnl`, `ssqsx`), each with a 3000 MB limit (a different, higher limit than Markis City Service's 1000 MB — apparently sized per customer). This is worth noting because it corrects Fact #14 below, which was specific to Markis and should not be read as universal:

| Time | `2j7b8` (the crashing pod) | `ssqsx` (a different pod) |
|---|---|---|
| 06:58:37 (before crash) | 273 MB | 280 MB |
| 07:03:43 | **1314 MB** | 282 MB |
| 07:08:50 | 1313 MB | 286 MB |
| 07:13:58 | 1319 MB | 328 MB |
| 07:19:06 | 1219 MB | **993 MB** |
| 07:24:13 | 1219 MB | 993 MB |
| 07:29:23 | 1220 MB | 1002 MB |

Two things stand out:
- **The crashing pod's memory never comes back down.** It jumps from 273 MB to 1314 MB within 5 minutes of the OOM and stays around 1.2 GB for at least 30 minutes afterward — `Restarts: 0` throughout, so nothing forces it to reset. The failed allocation attempt leaves the process in a permanently heavier state, at least over this timeframe.
- **A second pod shows the same kind of jump ~20 minutes later** (270-286 MB → 993-1002 MB), coinciding with JOAKIMS's escalating client-side heap and repeated retries, though this one never actually threw an exception — a near-miss, not a confirmed crash.

**Implication**: the freeze/crash cluster isn't just coincidence or a single shared mechanism — it's plausibly a feedback loop with two distinct ingredients. (1) A shared business task drives multiple employees to attempt the same expensive search in a short window — the human-behavior trigger. (2) Once a pod takes a big memory hit (whether it fully OOMs or not), it doesn't release that memory quickly, so it has less headroom for whichever colleague's request lands there next — a genuine technical amplifier on top of the behavioral trigger, not just retries happening to coincide. This also reconciles with Markis City Service: Markis runs a single pod, has never had an OOM crash, and its two checked freeze episodes stayed flat/idle — consistent with freeze clustering there being pure shared-timing, without this memory-carryover amplifier, since there's never been a crash on that pod to leave it elevated in the first place.

**Fleet-wide check**: is this Apollo-specific, or does it generalize? Joining every OrderCheck OOM crash in the last 30 days against its own crashing pod's memory just before vs. 15-40 minutes after finds **254 events with usable before/after samples** (~40+ distinct customers). On a representative 60-event slice of these:

- **56% show memory higher afterward, 44% show it lower** — a real skew toward "elevated," but far from a guaranteed outcome.
- The mean jump across that slice is a modest **+4.6 percentage points** (median +3.7pp), much smaller than Apollo alone suggested — pulled up by a skewed subset of large increases, offset by a comparably sized cluster of net decreases.
- **Zero of the 60 sampled events show a pod restart.** This part of the Apollo finding generalizes cleanly and universally — OOM crashes essentially never take the pod down; the process keeps serving requests regardless of what its memory does afterward.

Across the full 254-event set, **54 (21%) show a large lasting jump** (>20 percentage points of the pod's memory limit) — Apollo's case (+35pp) sits in this more dramatic tier, not the typical outcome. So: **the "crash leaves the pod measurably more fragile" mechanism is real and recurs in a meaningful minority of cases (roughly 1 in 5), not a universal law** — Apollo's incident happened to land on the dramatic end of a genuinely variable distribution.

**Does the size of that memory jump actually predict what happens next?** Comparing freeze-episode counts for the same customer in the hour before vs. the hour after each of the 254 crashes, split by whether it left a big memory jump:

| | n | Freezes/hour before → after (mean) | before → after (median) |
|---|---|---|---|
| Big jump (>20pp) | 54 | 16.2 → **21.1** (1.30x) | 11 → 7 (0.64x) |
| Smaller/negative jump | 200 | 20.7 → **14.6** (0.71x) | 13 → 3 (0.23x) |

Both groups start from similarly elevated freeze activity before the crash (consistent with the shared-business-trigger story — freezes are already happening as multiple people hit the same search), and both taper afterward as the initiating burst subsides. But the group whose pod stayed memory-heavy retains far more of that freeze activity (mean even *rises*, median only drops to 64% of its prior level), while the group whose pod recovered cleanly sees a much sharper decline (median drops to 23%). That's a directional, reasonably well-powered confirmation that it's specifically the crashes leaving the pod heavier that correlate with sustained or worsening freezes afterward, not crashes in general.

**Caveat**: this is an aggregate before/after comparison across many events, not a controlled regression — it doesn't rule out a shared third cause (e.g. a bigger burst of concurrent activity independently produces both a bigger memory jump *and* more freezes, rather than the jump itself driving the freezes). Still, the behavioral trigger (multiple employees hitting the same expensive search around the same time) remains the more consistently-observed half of the coupling story; the memory-carryover amplifier is real, situational, and now shown to correlate with worse downstream outcomes when it occurs.

**SQL-side check for this same incident**: Apollo's database sits in the `opterproductionnorway1` elastic pool. Pulling that pool's metrics for 2026-08-26 06:30–07:30 UTC (08:30–09:30 local) — the same window as the timeline above — gives a mixed but informative picture:

- **Data IO %**: flat, sitting in the same low 0-1% noise band as the rest of the day. No spike coincides with the incident.
- **CPU %**: a sharp, isolated spike to **~70%** landing almost exactly at 9:00 AM local — right at the 08:59:50 crash time — clearly standing above the already-elevated 30-50% morning baseline (CPU ramps up steadily from ~10% at 6 AM as the business day starts, a normal daily pattern, not itself evidence of anything; the spike is the outlier against that baseline, not the baseline itself).

This is a real, timing-matched signal, and it's different from what the pod-memory checks alone would have suggested: unlike Markis City Service's elastic pool (never exceeded ~40-50% CPU across a full week, see Fact #12), Apollo's pool *did* show meaningful CPU pressure exactly when this incident happened. It's not saturated (70%, not 100%), and it doesn't distinguish a genuinely CPU-heavy query plan from lock/latch contention (both would show up as elevated CPU) — that distinction needs Query Store's wait-stats, not resource metrics — but it means DB-side contention should not be treated as ruled out fleet-wide just because it didn't show up for Markis. It's customer/incident-specific, checked directly for two customers so far, with one showing a spike and one not. Plausibly the same shared-business-trigger burst that pushed Apollo's pod memory up also pushed its database CPU up at the same time — the app tier and DB tier both feeling the same concurrent-load event, rather than two unrelated stories.

## Other ServerApi OOM sources (why OrderCheck's count needed correcting)

Checking `Assembly == "Opter.Main.ServerApi"` for **every** `OutOfMemoryException` in the last 90 days, regardless of feature, splits cleanly into two groups:

| | Occurrences | Distinct customers |
|---|---|---|
| OrderCheck (complete definition — see methodology note above) | **636** | **133** |
| Everything else in ServerApi | **105** | **24** |

OrderCheck is ~86% of all ServerApi OOM crashes fleet-wide. The "everything else" bucket breaks down as:

| Source | Occurrences | Customers | Feature |
|---|---|---|---|
| `System.Data.Common.DecimalStorage.Get` | 34 | 1 | Unidentified — concentrated in a single customer hitting a different repeated OOM |
| `Opter.Main.Server.Dispatching.DispatchV2.ParseDataContainer` | 21 | 2 | Dispatch |
| `k2_stat_api_query_by_changed` (via generic `ExecuteDataSet`/`AdjustTimeZoneToLocalTime`) | 30 | 3 | Statistics API — bulk change-export over a wide date range |
| `System.Data.Common.Int32Storage.Get` | 9 | 2 | Unidentified |
| `k2_ods_get_order` (via generic `ExecuteDataSet`) | 5 | 4 | Single-order data-structure load |
| `Opter.Main.Order.AutoDispatching.AutoDispatch.GetRoutePlans` / `QueueItem` | 13 + 7 | 1 each | Auto-dispatch route planning |
| Long tail (~15 distinct causes) | ~1-4 each | mostly 1 | Scattered, various mechanisms |

**How the OrderCheck undercount was found**: the original filter (`Exception has "OrderCheck"` or `"LoadSearchResultModelsFromDataSet"`) missed every case where the `OutOfMemoryException` fires *before* control reaches OrderCheck's own C# code — specifically, inside `DatabaseAccess.ExecuteDataSet`'s generic post-processing step (`AdjustTimeZoneToLocalTime`, which walks the freshly-loaded `DataSet` adjusting date/time columns, itself unbounded and equally capable of exhausting memory on a large result set). When the crash happens there, the stack trace never contains the word "OrderCheck" — but the `Message` field logs the actual stored procedure invoked, and checking that revealed **300 of the 90-day total came from `k2_orc_get_all`/`k2_orc_get_all_by_all`** (OrderCheck's own stored procedure) despite not matching the original filter. The same generic `ExecuteDataSet`/`AdjustTimeZoneToLocalTime` code path is shared by several other features (Statistics API, single-order load), which is how those were discovered as genuinely separate, smaller sources.

**Implication**: the root-cause fix (row cap and/or streaming, see Recommended next steps) belongs at the shared `DatabaseAccess.ExecuteDataSet`/`AdjustTimeZoneToLocalTime` layer, not solely in OrderCheck's `LoadSearchResultModelsFromDataSet`. OrderCheck is overwhelmingly the biggest instance of this pattern, but not the only one — a fix scoped only to OrderCheck's `Clone<T>()` fan-out would leave the Statistics API, Dispatch, and auto-dispatch instances of the same underlying weakness in place.

## Open questions / not yet ruled out

- **Database vs. pod as the source of slow response — unresolved, and now a mixed result across the two customers checked.** Markis City Service's elastic pool showed no aggregate resource exhaustion on three metrics (CPU/IO/Workers) over a full week (Fact #12). Apollo Budbiler's pool, checked for the specific 2026-08-26 incident window, showed flat Data IO but a sharp, timing-matched CPU spike to ~70% right at the crash time (see "Behavioral and load coupling") — a real signal Markis's data never showed. So DB-side contention is not fleet-wide-ruled-out; it's customer/incident-specific, and it showed up for one of the two customers checked so far.
  - Lock/blocking contention is invisible to resource-percentage metrics and still hasn't been checked directly (would need Query Store or a live blocking-chain capture during an incident) — this remains the one thing that would actually distinguish "genuinely CPU-heavy query" from "blocked on a lock" for Apollo's spike.
  - Only two customers' databases have been examined so far (Markis, Apollo) — not enough to generalize either direction.
  - No actual execution plan for `k2_orc_get_all_by_all` has been pulled.
- **The .NET 9→10 idle memory baseline gap is now confirmed as a real, robust effect (not just correlation) — the specific GC mechanism behind it is still unverified.** The idle-moment check above (controlling for pod age and actual idleness, ~1000 pods, millions of samples) confirms `2025.12`/.NET 10 pods sit ~2.4 percentage points higher at true rest than `2025.06`/.NET 9, with newer .NET 10 branches (`2026.06`, `2026.07`) clustering the same way. - **Sample size caveat, updated**: with the corrected weekly counts and the corrected (complete) OOM definition, the `2025.06` (.NET 9) group ranges from ~270-280 customers down to single digits as the migration completes, vs. ~290-570 on `2025.12` (.NET 10). `2025.12` runs a higher incidence rate in 8 of 12 comparable weeks (`2025.06` higher in the other 4) — a real average gap (~1.35x) but not a rule that holds every week. So: related mechanisms sharing a common contributing factor (pod memory level), not fully independent, and not simply "one causes the other" either — both still most plausibly gated by a slow/blocked SQL query as the proximate trigger, with memory headroom affecting how often that query is slow enough to freeze.

## Hypotheses (plausible, unconfirmed)

- **.NET 10's Server GC commits more memory relative to the container limit than .NET 9 did, for the same workload, as a performance/throughput tradeoff.** The *effect* (higher idle memory baseline on .NET 10) is now confirmed directly (Fact #15, idle-moment check controlling for pod age and actual idleness — not just correlation across noisy windows). The *specific GC mechanism* remains the hypothesis part, unverified against .NET's actual release notes. Leading candidate explanation for the fleet-wide ServerApi memory-plateau shift (every `serverapi` pod, across ~1000 sampled production pods, climbs from ~150-230 MB at cold start to a higher settled plateau within 6-24 hours and stays there, with no restarts/crash-loops — i.e. not a leak in the classic sense, a sustained plateau, and higher on .NET 10 than .NET 9 even at genuinely idle moments).
- The `2025.06` → `2025.12` customer migration (now confirmed as a sharp two-week transition around 2026-08-17 to 2026-08-31, see "Evidence" section above) is why fleet-wide OOM/slowness incident *counts* have trended upward (31-59/week through June-July → 51-72/week by mid-to-late August, using the corrected complete OOM definition) — this mechanism is now directly supported by data, though the underlying *rate* difference between branches predates and is independent of the migration itself.
- **Slow SQL response is still the leading hypothesis for the proximate cause of freezes, but pod memory headroom is a probable contributing factor rather than a fully independent story.** (query-plan degradation on broad/unselective searches, from `k2_orc_get_all_by_all`'s forced `INNER LOOP JOIN` hints across `DEL_Delivery`/`SHI_Shipment`/`ADR_Address`/`RCU_ResourceCreditingUnit`.) Direct pod telemetry rules out *active* memory pressure during a freeze (see "Freeze mechanism"), but the fleet-wide crash-free check found pods already running ~2x the typical memory baseline in the minutes before a freeze starts (Fact #20) — consistent with a slow query taking longer specifically when the pod has less GC headroom to work with, rather than pod memory and SQL slowness being unrelated. Apollo's elastic pool independently showed a timing-matched CPU spike to ~70% right at its crash (see "Behavioral and load coupling"), a real DB-side signal not seen in Markis's data — one data point for, one against, on the "is it actually the DB" question. Still unconfirmed without an actual execution plan or blocking-chain capture — see Recommended next steps.

1. **Get [PR #13088](https://opter.ghe.com/code/Main/pull/13088) reviewed and merged.** It doesn't fix the underlying slowness or crash, but it converts "frozen, unresponsive application for up to 21 minutes" into "visible busy spinner while a slow operation completes" — a major UX improvement for the exact same underlying condition, ready to ship today.
2. **Confirm or rule out SQL-side contribution to the freezes**: get blocking-chain/Query Store access for one affected customer during a live incident, and pull an actual execution plan for `k2_orc_get_all_by_all` under a broad/unselective search. Moved up — this is diagnostic work, not a code change, and now targets the leading hypothesis for the freeze symptom specifically (see "Freeze mechanism" above: pod telemetry during two known freezes rules against memory pressure as the cause, pointing at the SQL query itself instead). Worth doing before investing in the bigger code fixes below, since it determines whether those fixes will actually address the freezes or only the OOM crashes. **Blocked as of this write-up**: direct Query Store T-SQL access was attempted for the Apollo incident and isn't available to this investigation. The Azure Portal's "Query Performance Insight" GUI feature (Intelligent Performance → Query Performance Insight, on the database resource itself) may work as a T-SQL-free alternative using the same resource-level access already used for the elastic pool metrics — worth trying before concluding this needs someone with elevated DB permissions.
3. **Replace `Clone<T>()`'s reflection fan-out in `LoadSearchResultModelsFromDataSet`** with a lean child-row DTO for the shipment/price-item fan-out, instead of duplicating the full 350-property object per child row. Bigger lift than #3, but it's the real architectural fix, and it benefits every feature sharing this pattern, not just OrderCheck (Statistics API, Dispatch, single-order load — see "Other ServerApi OOM sources" above).
